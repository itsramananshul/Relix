# Security Model

This document describes what the alpha actually enforces, in code, today.
What it does **not** enforce is in
[`current-limitations.md`](current-limitations.md). If you are evaluating
Relix for any deployment beyond a local developer machine, read both.

## Trust root

A Relix deployment is anchored on a single Ed25519 keypair: the
**org root**.

```
relix-cli identity init-org --root-key dev-keys/org-root.key --org acme
```

This writes two files:

- `dev-keys/org-root.key` — the 32-byte secret. Keep private.
  `.gitignore` covers `dev-keys/*.key`.
- `dev-keys/org-root.pub` — the 32-byte public key. This is the **trust
  file**. Every controller config references it in `[trust]
  org_root_key_path`. The controller refuses to load a 32-byte file as
  a public key if its length is wrong, and never accepts a secret-key
  file as a trust root by mistake.

The org id printed by `init-org` is `blake3(pubkey)` and is what every
identity bundle records as `org_id`.

There is exactly one trust level in the alpha. Hierarchical issuance
(IA → user) is post-alpha. See
[`current-limitations.md`](current-limitations.md) for the full list
of what the alpha does and does not do.

## Identity bundles

Every caller — a node, the bridge, the operator running `relix-cli` —
presents a signed `IdentityBundle` on every call. Mint with:

```
relix-cli identity mint \
    --root-key dev-keys/org-root.key \
    --name alice \
    --groups chat-users \
    --out dev-keys/alice.aic
```

The bundle is CBOR with a wrapping `Bundle` envelope and a payload
containing:

- `subject_id` — blake3 hash of the subject's Ed25519 public key.
- `name`, `org_id`, `role`, `clearance`, `groups[]`, `supervisors[]`.
- `bundle_id` — content hash of the encoded payload.
- header: `kid` (issuer pubkey), `not_before`, `not_after`, signature.

Lifetime defaults to 24h. Bundle verification happens **on the
responder** for every inbound call:

```
admission step 5: validate_identity_bundle(bundle, trust_root, now)
    -> verifies the signature with the configured trust root,
    -> checks not_before <= now <= not_after,
    -> rejects with error_kind = IDENTITY_INVALID on any failure.
```

No CRL, no revocation gossip — expired bundles fail the timestamp
check; short-lived bundles are the alpha mitigation.

## Transport

libp2p 0.54, protocol `/relix/rpc/1`, stack:

```
TCP  +  Noise XK  +  Yamux  +  request_response (CBOR codec)
```

Noise XK gives mutual peer authentication and confidentiality; each
peer's static key is its identity key. The wire payload is the CBOR-
encoded `RequestEnvelope` / `ResponseEnvelope`. The transport itself
is admission-agnostic — the dispatch bridge does the per-call work.

## Policy engine

Allowlist DSL, evaluated on the responder per call. Example
(generated by `scripts/relix-mesh-up.ps1`):

```toml
[admit]
groups = ["chat-users"]

[[rules]]
name = "ai_chat"
method = "ai.chat"
allow_groups = ["chat-users"]

[[rules]]
name = "tool_web_fetch"
method = "tool.web_fetch"
allow_groups = ["chat-users"]
```

Rules are matched per-method. A method with **no matching rule is
default-denied** — the dispatch bridge returns `error_kind =
POLICY_DENIED` and writes an audit record with
`status = denied`. The handler does not run.

`PolicyEngine::permissive()` exists for tests and admits any group,
but every method still has to clear the allowlist; running with no
policy file in production is operator error.

## Per-call admission pipeline

Source: `crates/relix-runtime/src/dispatch/mod.rs`. The pipeline runs
on every inbound `/relix/rpc/1` request:

1. **Decode envelope.** Malformed CBOR → `INVALID_ARGS` + error audit.
2. **Deadline check.** Now beyond `request.deadline + 30s` →
   `TIMEOUT` + error audit.
3. **Validate identity bundle.** Signature + lifetime against the
   configured trust root → `IDENTITY_INVALID` on any failure.
4. **Capability lookup.** No registered handler for the method →
   `UNKNOWN_METHOD` + error audit.
5. **Policy evaluation.** No matching allow rule → `POLICY_DENIED` +
   denied audit. **The handler is not called.**
6. **Dispatch.** Handler runs with verified caller identity + raw
   argument bytes.
7. **Audit.** Final record with status (`ok` / `error` / `denied`),
   policy decision string, and `error_kind` if any.

A handler can only ever observe step 6. Steps 1–5 are not bypassable
by handler code; steps 7 always runs.

## Audit log

Per-node, append-only, hash-chained. One record per inbound call.

```
dev-data/<run>-<node-type>/audit.log
```

Each record is CBOR with:

- `request_id` + `trace_id` (for cross-node correlation)
- `caller_node_id`, `caller_name`, `caller_groups`
- `responder_node_id`
- `method`
- `policy_decision` (`allow:rule_name` or `deny:rule_name:reason`)
- `status` (`ok` / `error` / `denied`)
- `error_kind` (one of the `error_kinds::*` constants when status ≠ ok)
- `latency_ms`
- `prev_hash` (blake3 of the previous record's bytes — chain link)
- `signature` (responder's Ed25519 signature over the record)

Inspect with:

```
cargo run -p relix-flow-inspect -- --audit dev-data/local-tool/audit.log
```

The hash chain detects post-hoc tampering. The per-record signature
is by the **responder** (the node that admitted or denied the call),
not the caller.

## Per-flow event log

Per-call audit lives on the responder; per-flow orchestration lives
on the caller. Every `flow-run` (and every chat request through the
bridge) opens a new event log at:

```
dev-data/flow-runner/flows/<flow_id>.log
```

Records (also CBOR, also signed):

- `FlowStarted` — flow path, trace id, identity issuer.
- `RemoteCallIssued` — per `remote_call`: peer alias, method,
  request id, arg byte length (log-before-act).
- `RemoteCallCompleted` / `RemoteCallFailed` — request id (cross-
  references the responder's audit), latency, body length OR
  error kind + cause.
- `FlowCompleted` / `FlowFailed` — terminal event with the VM exit
  value or the last `RemoteCallError`.

The bridge returns the flow log path in the response JSON so a
client can trace exactly what its request did.

## SSRF protections on the tool node

`tool.web_fetch` is the only capability that can dial arbitrary
external endpoints. It runs a defence-in-depth SSRF guard *before*
any HTTP I/O. Full details are in
[`tool-node-security.md`](tool-node-security.md). Summary:

- **Scheme allowlist.** `https` always; `http` only with explicit
  `[tool] allow_http = true`. `file://`, `ftp://`, `gopher://`,
  custom schemes — all denied.
- **Literal-IP range check.** Loopback, RFC 1918, link-local (incl.
  cloud-metadata `169.254.169.254`), shared-address-space, benchmark,
  documentation, multicast, broadcast, ULA, IPv4-mapped IPv6.
- **Hostname denylist.** Exact and suffix matches for `localhost`,
  `.local`, `.internal`, `.intranet`, `.lan`, `.corp`, `.home`,
  `.private`, `metadata.google.internal`, etc.
- **DNS validation.** Every IP the OS resolver returns is checked.
  A mixed-result resolution (some safe, some forbidden) is rejected
  whole. The resolver returns the validated address list to the
  caller; the caller does not pick "the safe one".
- **DNS pinning.** The actual TCP connect is pinned via
  `reqwest::ClientBuilder::resolve_to_addrs(host, &[SocketAddr])` to
  the IPs the guard validated. The URL keeps the hostname so the
  `Host` header and TLS SNI keep targeting the original origin.
- **Per-hop redirect re-validation.** A `reqwest::redirect::Policy::custom`
  closure runs the SSRF guard again on every redirect target. A
  `Location: http://127.0.0.1/` or cross-host `Location: http://attacker/`
  is rejected before reqwest follows it.
- **Secure client pool.** Reqwest `Client`s are cached by
  `(hostname, sorted_validated_addrs)`. Two requests share a Client
  only if their validated routes match. Naive global reuse is
  explicitly avoided because it would invalidate the DNS pin
  guarantee.

Failures surface as `policy_denied` (kind = 6) with the exact reason
string in the `cause` field. The bridge translates that into a 502
with the same string in the response body. The tool node's audit log
records every attempt (allow + handler outcome); the tool node's
tracing log records every redirect rejection as a structured WARN line.

## Fail-closed behaviour

- Missing policy file → `PolicyEngine::permissive()` and a startup
  WARN; **every method is still default-denied** until you add a rule
  for it. The permissive engine only relaxes the global `[admit]`
  groups check, not per-method allow rules.
- Missing identity bundle → admission step 5 rejects with
  `IDENTITY_INVALID` and the responder writes an audit record with
  caller `<unverified>`.
- Missing or invalid trust file → controller refuses to start.
- DNS resolution that returns no addresses, or any forbidden address →
  `tool.web_fetch` rejects without contacting the origin.
- Audit write failure → logged at `error!` level; the response still
  goes back (we do not silently drop responses), but the operator can
  spot the gap by counting tracing lines.

## What the alpha does **not** do

- **Manifests are not signed.** `NodeManifest` is plain CBOR at the
  wire level. The Gate 2 plan wraps it in `Bundle(BundleType::NodeManifest)`.
- **No revocation gossip.** An identity bundle can only be revoked by
  letting it expire. Default lifetime is 24h; tighten it for higher-
  risk roles.
- **No IA hierarchy.** One org root signs everything.
- **No outbound mTLS-style mutual auth for the tool node ↔ origin
  connection.** The tool node verifies the origin's certificate via
  webpki; the origin does not see a Relix client cert.
- **No rate limiting per caller** beyond what the policy engine
  expresses (allow / deny). Cost-class-aware rate limiting lands at
  Gate 2.

These are all listed in
[`current-limitations.md`](current-limitations.md) with rationale.

## Operator checklist before deploying

- [ ] `dev-keys/<run>-org-root.key` is on a machine you trust and
      backed up. Losing it means re-bootstrapping the entire mesh.
- [ ] Trust file (`<run>-org-root.pub`) is referenced consistently
      in every controller's `[trust] org_root_key_path`.
- [ ] Policy file has explicit `[[rules]]` entries for every method
      a caller will invoke. Methods without rules are denied.
- [ ] Audit log directory (`dev-data/<run>-<node-type>/audit.log`)
      is on durable storage and monitored. Operators relying on the
      audit chain should also ship the log off the host.
- [ ] AI / tool provider keys live only on their respective nodes
      (via `api_key_env` in the controller TOML). The bridge holds
      none.
- [ ] `[tool] allow_http` stays `false` unless a specific flow
      requires plain HTTP and the operator has accepted the risk.
- [ ] OS-level egress filtering: the tool node's process user should
      not be able to reach internal infrastructure beyond the
      hostnames you intend it to fetch.

## Agent gate (optional second admission step)

When the responder has agent profiles configured (see
[`agents.md`](agents.md)), an additional **agent gate** runs between
the identity-bundle check (step 3) and the policy evaluation (step
5). It compares the caller's subject_id against the agent ledger and
applies a five-phase check (status / surface allowlist / risk
ceiling / deny lists / allow lists), with an optional
"approval-required" path that pauses the call until an operator
approves it. The gate **narrows** policy, never widens it — policy
remains the floor. Empty agent ledger ⇒ gate is a no-op.

## HTTP bridge authentication

The bridge has its own auth layer, distinct from the mesh-side
identity-bundle pipeline above. Mesh callers prove who they are
via the signed `IdentityBundle`; bridge callers (curl, the
dashboard, OpenAI clients) prove who they are with a per-install
**bearer token**.

The token is 256 bits of entropy, hex-encoded, persisted at
`~/.relix/bridge-token` on first boot. Three routes are
intentionally unauthenticated:

- `GET /health`        — plaintext liveness probe.
- `GET /dashboard`     — the static HTML page.
- `GET /v1/auth/token` — one-time bootstrap so the dashboard can
  pick up its token at first load. The handler refuses callers
  that already carry an `Authorization` header.

Every other route, including the entire `/v1/*` surface and the
chat endpoints, requires `Authorization: Bearer <token>`.

**CSRF origin guard.** A second layer of defence for the
"malicious page on the operator's browser" threat. The middleware
rejects any request whose `Origin` header points at a host/port
other than the bridge's own loopback address. Curl callers
typically don't send Origin and pass through; cross-origin
browser tabs always send it and get rejected with 403.

**OpenAI shim exception.** `POST /v1/chat/completions` accepts any
non-empty bearer. OpenAI clients always send their own provider
key as the bearer, and the real provider key lives on the AI node
(not the bridge), so requiring the bridge token here would break
every OpenAI client out of the box without any security benefit.

**EventSource fallback.** SSE streams (`/v1/tasks/events/stream`,
…) can't carry custom headers from browser JavaScript, so the
auth middleware also accepts `?token=<token>` for those routes.
Loopback-only context makes this acceptable.

Implementation: `crates/relix-web-bridge/src/auth.rs`. The
dashboard's bootstrap JS lives at the top of
`crates/relix-web-bridge/src/dashboard.html` — it caches the
token in `sessionStorage` and patches `window.fetch` +
`window.EventSource` so per-call site changes weren't needed.

## Secret-file hardening

Every file that contains an operator secret is written at
restrictive permissions by code that flows through one shared
helper (`os_secure::restrict_to_current_user`):

| File                                | Owner             |
|-------------------------------------|-------------------|
| `~/.relix/bridge-token`             | `relix-web-bridge` |
| `~/.relix/config.toml`              | `relix-cli` setup  |
| `<data_dir>/bridge-secrets.toml`    | `relix-web-bridge` |
| `dev-keys/*.key`                    | `relix-cli` / bridge |

On POSIX the helper does `chmod 0600`. On Windows it shells out
to the bundled `icacls`:

```text
icacls <path> /inheritance:r
icacls <path> /grant:r <user>:F
```

Inheritance is stripped so a permissive ancestor can't grant
"Authenticated Users" read; the single granted ACE is the current
user with Full control.

We deliberately do NOT depend on the heavyweight `windows` crate
or `windows-acl` to call the Win32 ACL API. The bridge enforces
`unsafe_code = "forbid"`, and shelling out to `icacls` is
equivalent in effect, easier to audit, and adds no new
dependency.

## `relix doctor`

`relix doctor` connects to `/v1/health` and prints a PASS / WARN
/ FAIL report. It now also inspects the on-disk secret-file
permissions and surfaces any file that's looser than expected:

```text
PASS  secrets.bridge_token      ~/.relix/bridge-token — permissions restrictive
PASS  secrets.config_toml       ~/.relix/config.toml — permissions restrictive
PASS  secrets.bridge_secrets    dev-data/bridge-secrets.toml — permissions restrictive
```

WARN rows include the exact `chmod` / `icacls` command to
re-harden the file. Missing files emit a quiet PASS — a fresh
install has nothing to leak.

## Rotation

`~/.relix/bridge-token` regenerates only when the file is deleted.
To rotate: stop the bridge, delete the file, start the bridge —
a fresh 256-bit token is generated and printed in the boot
banner. The dashboard caches the token in `sessionStorage`;
refresh after rotation so it picks up the new value via the
bootstrap endpoint.

## If keys were ever committed

If any real provider key or libp2p secret was ever in a
git-committed `dev-keys/` directory (or anywhere in the repo's
history), **rotate it now.** Removing a key from `HEAD` does not
undo its presence in `.git/` history; the disclosure already
happened. Issue a fresh provider key via the provider's rotation
flow, and for Relix-issued libp2p secrets delete the old file
and let the next start regenerate it.
