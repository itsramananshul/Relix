**Rig / execution** - `rig.list`, `rig.describe` (name, label, governance, bridge-back + structured-output support, billing, and a **live readiness probe** + hint); per-Operative `rig`; `dispatch_batch` runs ready Briefs on their Rig via the timer loop. **Structured CLI readiness:** `ProcessRig::probe()` returns one of six honest statuses — `available` (binary present + a noninteractive `--version` ran clean) / `missing_binary` (not on PATH) / `not_authenticated` (the probe output carries a login nudge) / `unsupported_version` (the binary rejected `--version`) / `interactive_only` (the probe hung past an 8s timeout → needs a TTY) / `probe_failed` (spawn error or other failure). `classify_readiness` is a pure function over `ReadinessSignals`, unit-tested with mocked CLI outputs; the hint is the login hint for `not_authenticated`, the install hint otherwise. **Windows-safe resolution:** `resolve_program` resolves a CLI through `PATH` + `PATHEXT` into a `Spawnable` — a `Direct` `.exe`/`.com` (spawned straight) or a `BatchShim` `.cmd`/`.bat` (run via `%SystemRoot%\System32\cmd.exe /C <shim> <args…>` with **discrete argv**, no shell string) — preferring a real `.exe`, and treating an extensionless file as non-spawnable (so an npm `claude` *sh* shim sharing the PATH dir with `claude.cmd` is skipped, not spawned into `os error 193`). `probe()` and `run()` resolve identically, so the probe can never report a binary the runner can't launch; ProcessRig `fallback_paths` add the npm real launcher (`%APPDATA%\npm\node_modules\@anthropic-ai\claude-code\bin\claude.exe`). **Claude readiness is two-step:** `claude --version` then `claude auth status --text`, so `available` means installed AND logged in, an installed-but-logged-out CLI is `not_authenticated` (hints `claude auth login`), and an auth-check hang is `interactive_only`. **Codex readiness is also two-step:** `codex --version` then `codex login status` ("Logged in using ChatGPT" → `available — …; logged in`; "Not logged in" → `not_authenticated`). Gemini keeps the `--version`-only check (auth surfaces at run). **Honest limit:** for `--version`-only adapters `available` means "binary runs noninteractively", not necessarily "logged in". **Claude run behavior:** the Claude rig spawns `claude --print --output-format stream-json --verbose` with the Brief prompt on **stdin** (noninteractive; no TTY). The CLI emits JSONL — hook/system/assistant noise then a terminal `type:"result"` event carrying the real answer, `is_error`, and `permission_denials`. `parse_claude_stream_json` (`RigOutputFormat::ClaudeStreamJson`) extracts that event off the **raw, pre-redaction** stdout (so the JSON parses), then redacts + caps only the answer: `is_error` → a clear non-retryable failure (`subtype` + text); otherwise `Done` with the model's answer, where the summary **leads with `⚠ N tool permission(s) denied`** when Claude wanted a tool it couldn't run — Relix runs Claude **noninteractively and does NOT auto-approve tool use** (no `--dangerously-skip-permissions`), so file/command actions are blocked unless Claude itself already trusts the working directory. No terminal result event → fall back to exit-code handling (never a faked success). The result event is authoritative over the exit code. **Codex run behavior:** the Codex rig spawns `codex exec --json --sandbox workspace-write --skip-git-repo-check -` with the prompt on **stdin** (noninteractive). `--json` emits JSONL (`thread.started` → `turn.started` → `item.completed`* → `turn.completed`); `parse_codex_jsonl` (`RigOutputFormat::CodexJsonl`) takes the LAST `item.completed` of `item.type=="agent_message"` as the clean answer (no raw-JSONL dump) and maps an `error`/`turn.failed`/`thread.error`/error-item event to a non-retryable failure; no terminal event → exit-code fallback. `--sandbox workspace-write` confines the model's shell-command writes to the working directory — Relix pins that to the scoped run workspace — so **real coding work happens confined to the sandbox, never the repo**; `--skip-git-repo-check` because a scoped workspace is not a git repo. **Honest Codex-on-Windows caveat:** Codex's *shell-command* sandbox can fail to spawn on Windows (`windows sandbox: spawn setup refresh`), so shell tools (e.g. `ls`) may not run, though Codex's direct file-write tool does; this surfaces honestly inside Codex's own final message (captured in the run summary), not hidden. **Scoped per-run workspace:** every run now executes inside a dedicated sandbox folder — `<workspace_root>/<run_id>` (root = `<db_parent>/workspaces/runs`, overridable via `RELIX_RUN_WORKSPACE_ROOT`) — NOT the coordinator/repo CWD. `preflight_run` creates it after winning the Claim (`prepare_run_workspace`: the path is derived ONLY from the validated single-segment `run_id`, never from Brief content, so a prompt can't choose it and traversal is impossible; it drops a small trusted `BRIEF.md`), pins it as the child's `working_dir`, and persists it in the run ledger (`brief_runs.workspace`, surfaced in `/v1/runs` + the dashboard). A workspace-creation failure refuses cleanly (`workspace_error`) — releases the Claim, opens NO run record, and never falls back to repo-wide execution. `RELIX_RUN_WORKSPACE_MODE=inherit` is the only (explicit) opt-out back to coordinator-CWD execution. **Workspace context modes** (`RELIX_RUN_WORKSPACE_CONTEXT`, persisted in `brief_runs.workspace_context`/`_files`/`_bytes` + surfaced in `/v1/runs` + the dashboard, read via `run.workspace_config` → `GET /v1/spine/run-config`): **`empty`** (default, safest) gives the workspace only `BRIEF.md` — no project files; **`copy_repo`** copies a **capped, filtered** snapshot of the project (`RELIX_RUN_PROJECT_ROOT`, default coordinator CWD) into the sandbox so real coding work can happen WITHOUT repo-CWD execution. `copy_repo` is hard-bounded (`RELIX_RUN_WORKSPACE_MAX_FILES`/`_BYTES`, defaults 2000 files / 32 MiB — **exceeding either aborts and removes the partial copy**, so the prior 150GB local-bloat class of incident can't recur), and excludes dangerous/huge/generated dirs at any depth (`.git`, `target`, `target-audit`, `node_modules`, `dev-data`, `workspaces`, `worktrees` (covers `.claude/worktrees`), `dev-keys`, build caches) + secret/key files (`.env*`, `*.key`/`*.pem`/`*.p12`/`*.pfx`/`*.aic`, `id_rsa*`, `bridge-token`, `dashboard-admin.json`, `*secret*`/`*credential*`/`*password*`), respects top-level `.gitignore` names (best-effort) on top of those, and **skips symlinks** (no escaping the root / no loops). The project root is validated (real dir, never a filesystem/drive root) and is **operator config — the Brief prompt never chooses the root or any include path**. A context/cap failure refuses `workspace_context_error` (Claim released, no run record); basic-creation failure is `workspace_error`. (`git_worktree`/`git_checkout` context is **deferred / future** — only `empty` + `copy_repo` ship now, to keep scope + disk safe.) **Why repo-CWD execution stays unsafe + explicit-only:** running in the live repo lets an agent read/modify real source + tracked secrets and (for Claude) inherits the repo's tool-trust; `copy_repo` instead operates on a throwaway, secret-free COPY, so even a permitted write only touches the sandbox. **Honest caveat:** whether a tool action is permitted is decided by **Claude's own project-trust config**, not Relix — because a fresh scoped workspace is an untrusted Claude project, file/command tool use is **denied + surfaced via the `⚠` caveat** there (proven live: a "create a note" Brief in its scoped workspace left the repo untouched and recorded the denial), whereas a dir Claude already trusts would let the tool run. **Async dispatch:** `brief.run` is split into `preflight_run` (resolve adapter, refuse clearly without spawning, win the Claim, open the run record — all fast + synchronous) and `execute_ready` (the blocking `rig.run` + board advance + Chronicle + close record). The bridge handler pre-flights inline then hands `execute_ready` to a background thread, returning immediately with `status:"running"` + the `run_id`, so a long Claude/Codex Shift never freezes the bridge; the synchronous `run_brief_now` (heartbeat + tests) still runs both halves in-line. The `RunReport` status distinguishes accepted (`running`) + real outcomes (`done`/`failed`/`continued`) from clear pre-run refusals (`not_found`/`unassigned`/`no_adapter`/`adapter_unavailable`/`already_running`). **Run ledger:** a durable `brief_runs` table (one row per Rig execution: `run_id`/`brief_id`/`agent_id`/`rig`/`status`/`started_at`/`finished_at`/`duration_secs`/`summary`) is opened on commit and closed on terminal; a pre-flight refusal records **no** row. `brief.runs` lists recent runs (empty arg) or a Brief's history (id arg). **Run transcript:** a focused, capped `run_events` table (event_id / run_id / ts / kind / source / message / payload_json / redacted) records *what happened* in a run — the lifecycle (relix source: `accepted` → `workspace_prepared` → `process_started` → `process_exited` → terminal `result`/`failed`/`continued`/`cancelled`) PLUS parsed adapter events (`claude_events`: assistant_message / tool_use / result / permission_denied / usage cost / error; `codex_events`: thread/turn lifecycle / agent_message / command / file_change / error; raw adapters: a compact `output`/`stderr` event). It is **never the raw JSONL** — every text field is secret-redacted + length-bounded, `append_run_event` enforces a per-run cap (`MAX_RUN_EVENTS=400` → one `truncated` marker then drop) and a per-field byte clamp. The `Rig` contract gains an additive `run_transcript` (default wraps `run` with no events); `ProcessRig` shares one `execute` body. **Cancellation (real):** a global `CancelRegistry` (run_id → `AtomicBool`) is registered at pre-flight; `ProcessRig`'s wait loop polls the flag (lock-free) and **kills the child** on cancel; `execute_ready` then reports the run `cancelled` (not failed). `run.cancel` flips the flag, records a `cancel_requested` event, and returns `active` truthfully (a live process was signalled vs already finished) — no fake cancellation. **ProcessRig** spawns with safe argv (no shell), a hard timeout + child-kill (timeout + cancel), streamed capture, a validated working directory, and **secret redaction** of captured output. **Reviewable run results (artifacts + review):** after a run finishes, `execute_ready` detects WHAT THE AGENT CHANGED by diffing a BEFORE manifest (captured at pre-flight) against an AFTER scan of the scoped workspace into `created`/`modified`/`deleted` rows in a `run_artifacts` table — **metadata + path references only, never file content in SQLite** (run_id/brief_id/workspace/rel_path/kind/size/hash/is_text/captured_at). The scan reuses the workspace copy filters (no `.git`/`target`/`node_modules`/`dev-data`/secrets/`.env`/key files), **skips symlinks**, content-hashes only files ≤ 1 MiB (deterministic `DefaultHasher`), caps the walk + the recorded count (`MAX_RUN_ARTIFACTS=1000`), and **NEVER scans the repo** — `inherit` (non-scoped) runs are skipped entirely. `BRIEF.md` / copied context only appear if the agent actually edited them. Failures surface as `artifacts.scan_failed` (alongside `artifacts.scan_started` / `artifacts.detected` with counts) — never swallowed. **Review state:** a `done` run opens `pending_review` (`brief_runs.review`/`review_note`/`reviewed_at`); `set_run_review` records `accepted`/`rejected` (only for `done` runs) + a `review` transcript event. **Safe apply (SHIPPED):** an `accepted` run's changed files can now be applied back into the configured project root (`RELIX_RUN_PROJECT_ROOT`, the same operator-config root `copy_repo` snapshots from) — guarded, path-safe, conflict-checked, idempotent, tested. `build_apply_plan` produces a **pure preview** (`run.diff` → `GET /v1/runs/:id/diff`, never mutates files): a per-file plan (`action` = `create`/`overwrite`/`delete`/`noop`/`refuse`, `can_apply`, `conflict`, `reason`) plus whether the run is **apply-eligible** (`run_apply_eligibility`: `done` + `accepted` + a scoped workspace — `inherit`-mode / legacy / unreviewed / rejected runs are refused, with nothing of theirs ever applied). **Conflict detection** compares each target against the run's BEFORE-run baseline: a new `run_artifacts.baseline_hash` (the before-scan content hash, persisted for `modified`/`deleted`; `None` for `created` / files > 1 MiB) lets apply confirm the project-root file still matches what the run started from. The rules are conservative — *better to refuse than overwrite blindly*: `created` applies only if the target is absent (or already byte-identical → `noop`), and **refuses if the target exists with different content**; `modified` applies only if the target still equals the baseline hash (or already equals the new content → `noop`), and **refuses if the target is missing, diverged, or the baseline is unverifiable** (incl. files too large to hash); `deleted` removes only if the target still equals the baseline (or is already absent → `noop`), else refuses. Paths are re-validated at apply time (reject absolute / `..` / drive-letter / UNC / empty-component paths and the same excluded dirs/files the copy filter uses — `.git`/`target`/`node_modules`/secrets/…), and the resolver **refuses any path that escapes the root or crosses a symlink** (no traversal, no symlink-target overwrite). `apply_run` (`run.apply` → `POST /v1/runs/:id/apply`) **refuses the WHOLE apply if ANY file is unsafe/conflicted** (no partial apply, no `force`), otherwise copies `create`/`overwrite` files (creating parent dirs) + removes `delete` files, and is **idempotent** (re-applying an already-applied plan is all-`noop` → 0 writes, no corruption). A durable apply ledger on `brief_runs` (`apply_status` = `not_applicable`/`blocked`/`ready`/`applied`/`failed`/`conflicted`, `applied_at`, `apply_note`, `applied_files`, `failed_files`) records each attempt; transcript events `apply.plan` / `apply.started` / `apply.applied` / `apply.conflicted` / `apply.failed` narrate it. A zero-artifact accepted run is a clear `applied` no-op. Bridge: `GET /v1/adapters` (rig.describe), `POST /v1/spine/briefs/:id/run` (brief.run), `GET /v1/runs` (recent run ledger), `GET /v1/runs/:id` (one run), `GET /v1/runs/:id/events` (the chronological transcript), `POST /v1/runs/:id/cancel` (cancel a running run), `GET /v1/runs/:id/artifacts` (changed files), `GET /v1/runs/:id/artifacts/:aid/preview` (a safe text preview — server-resolved path verified UNDER the workspace, binary/large/missing refused, secret-redacted, size-limited to 64 KiB), `POST /v1/runs/:id/review` (accept/reject), `GET /v1/runs/:id/diff` (the safe-apply plan + eligibility), `POST /v1/runs/:id/apply` (apply an accepted run's changes), `GET /v1/spine/briefs/:id/runs` (a Brief's Shift history). ## Governance And Security Carried Through

- Default-deny agent gate; a pending hire is inert.
- Heartbeat Rig resolution now refuses non-active Operatives before dispatch, so pending/suspended/disabled hires cannot run through the default-Rig path.
- Heartbeat wake admission now checks the assigned Operative's `wake_on_timer` flag and `max_concurrent_runs` cap before claiming queued work.
- Tenant-scoped spine reads for Mandates/Campaigns/Guild state.
- Org tree is cycle-guarded.
- Thin Rigs are governed at the box boundary and through scoped bridge-back tokens.
- Bridge-back tokens are scoped per Shift, Brief, Operative, and method; tokens are checked by `bridge_back.authorize`, exposed only through narrow HTTP routes, and revoked when the Shift ends.
- Thin Rigs can raise a real Brief-linked Clearance through `brief.clearance_request`; the handler derives subject/approver metadata from the stored Operative profile, parks the Brief in `awaiting_input`, and writes a pending `approval_requests` row.
- Macro execution is allowlisted and `ProcessRig` stdout is capped.
- Hard dispatch failures park the Brief in `blocked` and Chronicle the reason.
- Strategy gate is queryable and tenant-guarded. The explicit `agent.request_hire_for_mandate` team-build path refuses until the Mandate strategy is approved; it now *also* applies the spawn Key. `agent.create` is operator-only (an agent actor is refused). Legacy/manual `agent.request_hire` does not check a Mandate but does enforce the spawn Key.
- Spawn Key (company-model §5.2A) is **enforced**: an agent actor calling `agent.request_hire` / `agent.request_hire_for_mandate` is allowed only with `can_spawn_agents`; the hire is always pending-inert (never live). The Founder/Board (operator/admin) bypasses. An actor with no Operative profile in the Guild is security-denied. `agent.create` (live creation) is operator-only.
- **Route-differentiated spawn Clearance** (company-model §5.2A): `spawn_route=lead/founder` now mints a real typed Clearance (`approval_requests` row, `method = agent.activate_hire`, `agent_id = the pending hire`) linked to activating the hire. The hire stays pending-inert until the Clearance is decided: `coord.approval.decide` activates the hire on approve (`approve_hire`) and disables it on reject (`reject_hire`). `route=lead` widens the deciders to the actor's Lead (operator/admin always allowed); `route=direct` and operator hires mint NO Clearance.
- Assign Key (company-model §5.2B/§5.3) is **enforced at every assignment path**: `brief.set` (field=assignee), `brief.create` (initial assignee), and `brief.move` (into `in_progress`/`in_review`, against the Brief's current assignee). `enforce_assign_key` is the single tenant-scoped chokepoint with three layers: (1) the non-operator caller must have an Operative profile in this Guild; (2) **assignee validity** — the assignee must exist in this Guild and be `active`, so cross-tenant/unknown ids and disabled/pending/suspended hires can no longer receive executable work; (3) the actor's `can_assign_work` + `assign_scope` (any / branch via the tenant-scoped org tree / specific). Short-circuits to allow for: empty assignee (clearing), the Founder/Board (operator/admin, sovereign), and assignee == actor (claiming/progressing one's own work). `agent.assign_check` exposes the verdict read-only.
- **Tenant isolation (GROUP 6)** on the product agent/governance surface: `agent.get/keys/update/delete`, `agent.reports/peers/by_role/branch/line/manages`, `agent.assign_check`, `agent.allowance_committed`, and `coord.approval.pending/get/decide` all scope by the caller's verified tenant. A known agent_id/approval_id from another Guild resolves to not-found — never a cross-tenant read/write. The bridge forwards the tenant; the unscoped store methods remain only as internal/gate helpers.
- **Inline Clearance decide**: `POST /v1/spine/clearances/:id/decide` forwards to `coord.approval.decide` as the bridge's own verified identity (same path as `/v1/approvals/:id/decide`); the runtime cap enforces `authorized_approvers` ∪ operator/admin, so this never fabricates approval. The runtime refuses to re-decide a terminal approval (`decide_approval` requires `status='pending'`) and the decide handler returns before the spawn-Clearance activation hop, so side effects (activating a pending hire) apply **exactly once**. A cross-tenant `approval_id` resolves to not-found. There is intentionally no per-decision `ttl_secs` knob — the minted token's TTL is controller-configured.
- **Prime team-build foundation** (`mandate.team_plan`): a single governed step (NOT an autonomous loop). Requires an approved Mandate strategy + the actor's spawn Key; **persists** the plan (`mandate_team_plans`) and returns a structured JSON plan (`plan_id`, `status`, `proposed_roles`, `pending_hires`, `clearance_ids`, `denials`, `next_steps`), minting pending hires (with spawn Clearances) for roles supplied with an identity. `mandate.team_plan.latest` reads the newest persisted plan; `mandate.team_readiness` recomputes live readiness (missing roles / pending clearances / active agents / pending hires / blocked roles / next action) from the current hire and Clearance states — so approving a spawn Clearance and activating its hire makes the Mandate view show the team becoming active without mutating the plan row. All three are tenant-scoped.
- **Prime Mandate-to-Brief orchestration** (`mandate.orchestrate`, company-model §4.6): deterministic, non-LLM. Arg `mandate_id|mode?|max_briefs?|dry_run?` with modes `plan_only` (default; report-only) / `create_briefs` / `assign_ready`. Gate 1 = approved strategy (without it **nothing** is materialised). Materialisation is then **per-role**, not whole-team: with the strategy approved and a building mode (`create_briefs`/`assign_ready`), orchestration lays down a parent + a role-track Brief for **every** planned role, and an executable subject Brief only for the roles that are actually **active**. An **idempotent, three-tier** Brief tree: one parent `Execute Mandate: <title>` → one **role-track** Brief per role (known roles get a named track, e.g. `Engineering track: …`; unknown roles get `Execute <role> track for <mandate>`) → one **subject-execution** Brief per active agent under its (active) role track (e.g. `Engineering execution: <agent_id>`). Role tracks link under the parent and **stay unassigned**; subject Briefs link under their role track and are the items `assign_ready` assigns. **Placeholder role tracks:** a role that is **missing / pending-hire / pending-clearance / denied / blocked** still gets a durable role-track Brief under the parent — titled `… track blocked: <reason>` (e.g. `crew not ready`, `pending hire`, `pending clearance <approval_id>`), tagged `placeholder:true` + `reason` on its run entry, given a `blocker` Dossier explaining why — but **no** subject execution Brief and **no** assignee. **Role-keyed clearances:** a spawn Clearance records the pending hire's `agent_id`; `compute_readiness` maps that back to the seat's role (via the plan's pending hires) and stamps `role` + `agent_id` onto each `pending_clearances` entry, so a Clearance-blocked seat gets its own placeholder (reason naming the approval id) rather than only an unattributed JSON blocker. The most specific reason wins per role (pending clearance → pending hire → missing → blocked). A placeholder shares the role marker, so when the role later becomes active the **same** role track is reused and gains its subject Brief (the placeholder→active transition). **Placeholder title lifecycle:** on that transition the role-track title is **auto-promoted** from `… track blocked: <reason>` to the normal `… track: <mandate>` title — but only when the current title is still the machine-written placeholder form (detected by the `… track blocked:` prefix); a hand-edited title is detected as non-auto and **preserved**. The whole-team `ready` flag still drives the reported `status` (`blocked` while any gap remains) and next-actions. **max_briefs overflow visibility:** role tracks are capped at `max_briefs - 1` (parent counts as one) with active tracks prioritised; any placeholder role that does not fit is **not** silently dropped — it is reported in `placeholder_tracks_omitted` (`{role, reason, omitted:"max_briefs"}`), mirrored into the persisted `skipped` list, and surfaced as a next-action + a dashboard warning. (If active roles alone exceed the cap, the surplus active roles are still dropped — a documented edge for very large teams under a tiny cap.) Mandate-link is preserved on every tier and a newly-created parent gets an orchestration Dossier. `assign_ready` assigns each active agent's subject Brief through `enforce_assign_key` (the real assign gate — operator bypasses, an agent actor is gated); a denial/failure is recorded in `skipped`, never panics. **Idempotency (stable, subject-aware source markers):** every orchestrated Brief carries a `source_kind = "mandate_orchestration"` + a `source_marker` (the `tasks.source_kind`/`source_marker` columns). Markers are derived from the Mandate id, **not** from title text: parent `mandate:{mandate_id}:parent`, role track `mandate:{mandate_id}:role:{role_key}`, subject execution `mandate:{mandate_id}:role:{role_key}:subject:{agent_id}`. A rerun looks up each Brief by marker (`get_brief_by_source_marker`), reuses the marked tiers, and creates only the missing ones (`create_brief_with_marker`); a reused Brief's **title is left untouched** so a manual rename is never clobbered. This makes orchestration robust to a **Mandate rename**, a **manual Brief-title edit**, and a **partial crash** (any missing tier — parent-only or parent+role-track — is filled on rerun). A **changed active agent** for a role yields a new subject Brief (its agent-keyed marker) while the role track above is reused; the same agent on a rerun reuses its subject Brief. **Back-compat:** the previous slice's role-only marker (`…:role:{role_key}`) *is* the role-track marker, so legacy role-only children are reused as role tracks with no duplication. The deterministic `input_signature` (`DefaultHasher`, fixed seed) is computed over all markers (parent + role + subject) + mode + plan id, so it is rename-stable and reflects staffing changes. Every run persists via `record_orchestration_run`; `mandate.orchestration.latest` / `.list` read them back (tenant-scoped). The response carries the tiered view `{parent_brief, role_tracks_created, role_tracks_existing, placeholder_tracks_created, placeholder_tracks_existing, placeholder_tracks_omitted, subject_briefs_created, subject_briefs_existing, assigned_briefs, skipped, blockers, source_markers, next_actions}` plus the backward-compatible flat `created_briefs` / `existing_briefs` (unions, each entry tagged with its `marker`, and placeholder entries additionally tagged `placeholder:true` + `reason`). The run record persists `created_brief_ids` / `existing_brief_ids` (reused) / `assigned_brief_ids` / `skipped` / `source_markers` / `blockers` / `input_signature` — each created/existing entry keeps its `marker` (and `placeholder` flag), so the tier (parent / role / subject / placeholder) is recoverable from the persisted run without extra columns. **Tenant note:** the `tasks` table now carries a row-level `tenant_id` (Guild) column. Product-spine Briefs are stamped at creation (`create_brief` → `set_task_tenant`); legacy rows and non-Brief Tasks are NULL and resolve to the `default` Guild via `COALESCE(tenant_id,'default')` in the tenant-scoped reads, so existing single-tenant DBs keep seeing every row while a *named* Guild sees only its own. The product **board / inbox / detail / search / label** read capabilities (`brief.board`, `brief.board_summary`, `brief.blocked_list`, `brief.stale_list`, `brief.overdue`, `brief.unassigned`, `brief.search`, `brief.by_label`, `brief.detail`) call `*_for_tenant` store variants with the caller's `ctx.tenant_id_or_default()`, so a known Brief id from another Guild reads as not-found and never appears on another Guild's board/inbox. **Same-tenant ownership on every exposed Brief surface:** a `deny_cross_tenant` guard (built on `task_in_tenant`) runs **before** the Brief-row mutations and relationship/Dossier operations. **All** Brief row reads and mutations currently exposed through the product-spine handlers now enforce same-tenant ownership: the mutations `brief.set`, `brief.move`, `brief.comment` (communication is not authorization-free across Guilds — a cross-Guild comment is refused and **no** Chronicle event is appended), `brief.set_labels`, `brief.set_due`, `brief.pin`, `brief.snag` / `brief.unsnag` (both the blocked Brief AND its blocker), `brief.set_snags`, `brief.dossier_add`, `brief.subbrief` / `brief.unsubbrief` (both endpoints); and the reads `brief.detail`, `brief.fields`, `brief.labels`, `brief.due`, `brief.blocked`, `brief.snags`, `brief.dossiers`, `brief.dossier_latest`, `brief.dossier_get` (resolved via the Dossier's owning Brief), `brief.subbriefs`, `brief.subbrief_progress`, plus the reverse-edge reads `brief.blocking` / `brief.parents` which use tenant-scoped store variants (`list_blocking_for_tenant` / `parent_briefs_for_tenant`, a JOIN on `tasks` filtered by Guild) so a related Brief from another Guild is never leaked even if a legacy edge crosses tenants. A cross-Guild target returns the **same not-found** a genuinely-missing Brief would, so the row's existence in another Guild is never leaked. Brief creation treats the tenant stamp as **required**: `create_brief` rolls the freshly-created row back and returns an error if `set_task_tenant` fails, so a stamp failure can never silently leave an unscoped Brief (the human-ref `assign_brief_ref` stays fail-soft — it is a display-only `REL-N` id whose absence does not make a Brief unusable). **Remaining honest caveats:** `mandate.briefs` / `list_briefs_by_mandate` still rely on the globally-unique, tenant-validated `mandate_id` (not a row tenant filter); and the marker-based orchestration dedup remains keyed on the `mandate_id` embedded in the marker (also tenant-validated upstream).

- The Prime/CEO flow now spans plan → readiness → **orchestration**: `mandate.team_plan` (persisted), `mandate.team_readiness` (live staffing), and `mandate.orchestrate` (turns an approved + ready Mandate into an idempotent, governance-respecting Brief tree, assigning the active team, persisting each run). It is **still not autonomous** — every step is operator/Prime-initiated per call; there is no driver that proposes a strategy, gets it greenlit, and stands up + orchestrates a whole team on its own. The Brief breakdown is **deterministic/rule-based, not LLM** (fixed role→title map; a three-tier parent → role track → per-agent subject execution tree; no decomposition, dependencies, or authored content). Idempotency uses **stable, subject-aware source markers** (Mandate-id + role + agent-derived), so renaming a Mandate, hand-editing a Brief title, swapping the active agent, or crashing mid-run no longer orphans or duplicates the tree — a changed agent gets its own subject Brief while the role track is reused, and any missing tier is filled on rerun. Missing/pending/blocked roles now get **durable placeholder role tracks** (a role-track Brief titled `… blocked: <reason>` with a `blocker` Dossier, but no subject execution Brief and no assignee); when the role later activates, the same role track is reused and gains its subject Brief. Work is still **refused per-role** until that role is active — placeholders are never assigned.

### Adapters And Hermes

- Tether / plugin-hook system is unbuilt. The existing plugin host is an out-of-process capability-provider system, not the in-process lifecycle-hook bridge described in `relix-hermes-integration.md`.
- Hermes rich seam is unbuilt. `hermes_rig` is a stdio placeholder and remains `BoxLevel`; real `/v1/runs`, MCP, `relix-bridge`, and PerToolCall governance are future work.
- CLI adapters declare structured-output flags and metadata, but do not parse stream-json/JSONL yet. Missing: token/cost capture, `$0-but-tracked` cost ledger rows, quota polling/back-off, Codex per-tenant `CODEX_HOME` symlink, session resume, interrupt, and stop.
- Bridge-back exists for the narrow universal floor: comment/Sub-brief/Dossier/Snag/Clearance/claim-holder routes. Thin adapters still have no per-tool-call governance; Clearance is the route for an adapter to ask Relix before crossing a boundary it cannot gate internally.

### Dashboard

- The current dashboard is an interim single-file shell, not the decided React SPA in `relix-dashboard-design.md`.
- The page now follows the work-object IA, but it lacks a componentized router, query cache, tenant-prefix navigation, and surgical realtime invalidation.
- The Desk/Inbox and the Brief live work thread now exist (sectioned needs-attention Desk, claim holder, Chronicle timeline, Operative Desk), but only as request/response reads in the interim shell — there is no websocket-driven realtime, transcript/interaction streaming, or push invalidation; the thread refreshes on open/comment.
- The per-Operative Keys panel exists (enforced spawn/assign Keys + stored-only manage/configure/secrets/charter). Pending Clearances render on the Desk **with inline Approve/Reject** (`POST /v1/spine/clearances/:id/decide`, forwarded as the bridge identity; the runtime cap enforces authorisation). The Mandate panel has a **"Plan team"** action, renders the **persisted latest plan + live team readiness** (`mandate.team_plan.latest` + `mandate.team_readiness`), and gains an **Orchestrate** action (Plan / Create briefs / Create + assign) that renders the latest persisted orchestration run — broken out by tier (parent, role tracks created/reused, placeholder/blocked tracks created/reused with reasons, subject-execution Briefs created/reused, assigned, skipped/blockers, next actions; tiers are derived from each Brief's source marker + `placeholder` flag) — and refreshes the board after a run.
- Missing or partial surfaces: pan/zoom Lattice org chart, full Costs/Approvals with spend enforcement controls, full issue-as-live-chat-thread detail with run transcripts/interactions, Settings hub, and websocket-driven realtime.
